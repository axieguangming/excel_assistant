# 评测口径

本文件定义本项目如何评测模型，以及为什么当前口径是这样。它同时记录一次口径修正的过程：修正前后同一个模型可以相差 45 个百分点，因此**口径不统一的评测结果不可用**。

配套内容：三模型对照实验报告见 [experiment-2026-11-02.md](./experiment-2026-11-02.md)，历史实验数据见 [finetune-experiments.md](./finetune-experiments.md)，后续工作见 [next-steps.md](./next-steps.md)。

## 1. 为什么要专门定义口径

已有评测在这几条上出过问题，全部是真实发生过的：

| 问题 | 后果 | 状态 |
| --- | --- | --- |
| 测试集与训练集共用同一套模板句式 | v1 得 100%，同一模型在独立集上只有 30.4% | 已识别，改用留出链集 |
| 不可完成请求只判「是否调用工具」 | 从不调用工具的模型自动满分，v2 与基座均得 18/18 | **已修正**，v2 实为 10/18 |
| 只测 test，不测 train/val | 无法区分欠拟合与泛化不足 | 待补 |
| 缺强模型对照组 | 无法判断 78.8% 距上限多远 | **已补**，见 2.3 |
| 浮点比较用固定 6 位小数 | 2.7e10 量级下把正确结果判错 | 已修正 |
| 跨数据集并排比较不同模型 | 「v1 100% → v2 78.8%」实为不同测试集 | 已识别 |
| 评测问法与系统提示冲突 | 按提示澄清计数口径的强模型被判 40% | **已修正**，见 6.4 |
| `describe_data` 覆盖中间结果 | 强模型「先看数据」后全线失败，80% → 20% | **已修正**，见 6.8 |
| 只读的 `describe_data` 多调用一次判失败 | 谨慎的模型被扣分 | **已修正**，见 6.7 |

## 2. 对照组必须完整

### 2.1 三个模型的定位

三个组合是**同一基座 + 不同适配器**，不是三个模型：

| 名称 | 构成 | 训练数据 | 用途 |
| --- | --- | --- | --- |
| 基座 | `Qwen2.5-1.5B-Instruct` 原始权重 | — | 能力下限 |
| v1 适配器 | 基座 + `build/lora-out` | 规则链 600 条、1200 样本、7 个模板句式 | 历史对照，已停止使用 |
| v2 适配器 | 基座 + `build/lora-expanded` | LLM 链 1000 条、4664 变体、3934 样本 + 147 澄清 | 当前基线 |

### 2.2 v1 不参与跨数据集比较

v1 在规则分布上训练。拿它测新数据集，结果是「没学过这个分布」，不反映能力差异。

v1 与 v2 唯一公平的对比场合是**留出链集**，因为该集合独立于两版训练分布：

| 模型 | 留出链集（32 条） |
| --- | --- |
| v1 | 30.4% |
| v2 | 71.9% |
| 基座 | 0%（等价类 0/23） |

### 2.3 强模型上限（已补）

`deepseek-flash` 已接入 `finetune/eval_sft.py --base-url`，走同一个 Agent 图、同一套工具、同一评测口径。实测（396 条留出集）：

| 数据集 | 强模型 | v2 | 是否显著 |
| --- | --- | --- | --- |
| 留出集 A（新数据值，247 条） | 85.4% | 79.8% | 不显著（p=0.097） |
| 留出集 B（新表结构，149 条） | 81.2% | 66.4% | **显著**（p=0.0037） |
| 合计（396 条） | 83.8% | 74.7% | — |

强模型是当前最强的对照组，但它并不是「本项目的上限」：

- 它**不遵守项目定死的工具协议**——会多调 `describe_data`（已通过 6.7 归一）、多调 `aggregate_data` 重算、或把「按分类」自行替换成别的筛选条件。
- 结果是它在**单步任务上明显弱于 v2**（A 组 61.9% vs 100%，B 组 42.9% vs 100%）。
- 反过来 v2 在**澄清类上明显弱于它**（91 条：74.7% vs 97.8%，B 组差 45 个点）。

所以「距上限多远」这个问题不能拿它当分母，详见 6.5。两者是互补关系，不是替代关系。

## 3. train / val / test 三层

### 3.1 现状

| 分区 | 样本数 | 已做的评测 |
| --- | --- | --- |
| train | 3934 | **从未评测** |
| val | 498 | **只记录 `eval_loss`（0.1006）**，未跑 Agent 评测 |
| test | 499 | 完整 Agent 评测 |

### 3.2 三层各自回答什么

| 分区 | 回答的问题 | 用途 |
| --- | --- | --- |
| train | 模型能不能复现它见过的东西 | 诊断欠拟合 |
| val | 调参时的泛化信号 | 选超参、早停；**不应反复用 test 调参** |
| test | 最终泛化能力 | 只在定稿时看一次 |

判断逻辑：

| train 准确率 | 差距（train − test） | 结论 | 措施 |
| --- | --- | --- | --- |
| ≈ test（约 78%） | 小 | 欠拟合，连见过的都复现不了 | 加训练量/调超参；**加数据无用** |
| ≥ 95% | 大 | 记住了但不会迁移 | 加数据多样性、正则化 |
| 约 85% | 中 | 混合问题 | 两者都要 |

建议规模：train 按步数分层抽 400 条、val 全量 498 条。train 全量跑一次约 7.6 小时，不现实。

### 3.3 曝光偏差：`eval_loss` 不能当准确率

`eval_loss` 0.1006 表示 teacher-forcing 下每步都有标准答案可参照时，逐 token 预测得很准。但自由运行 Agent 时每步依赖模型自己的上一步输出，一步错则步步错，实测只有 78.8%。

**汇报时必须区分**：`eval_loss` 是训练内部指标，任务成功率是业务指标，两者不能互相替代。

## 4. 结果比较的数值精度

### 4.1 已修正：固定 6 位小数

旧实现把数值格式化成 6 位小数再比较字符串。在 2.7e10 量级的汇总值上，float64 的分辨率（约 3.8e-6）已经粗于 1e-6 的量化步长，数学上相等的结果会落在量化边界两侧：

```
期望 CSV: 27103570497.560001
实际计算: 27103570497.559998
差值:     3.814697265625e-06   ← 1 个 ULP
```

实测因此误判 2 条（120 条测试集上）。现改为 **12 位有效数字**（`f"{value:.12g}"`），并对 `-0.0` 归零。

### 4.2 当前做法

| 项 | 规则 |
| --- | --- |
| 数值 | 12 位有效数字，相对精度比较 |
| 日期 | 统一格式化为 `YYYY-MM-DD` 或 `YYYY-MM-DD HH:MM:SS` |
| 空值 | 统一为空字符串 |
| 行顺序 | 默认按有序比较；顺序不同单独报 `行内容一致但顺序不同` |
| 列名 | 结果表比较**按列位置**，不比较列名 |

列名的处理原则：聚合与计算列的名称是模型自由决定的（`销售额合计` 与 `销售额_sum` 等价），只要数据一致就算通过。

## 5. 澄清与不可完成请求

### 5.1 旧判据的缺陷

旧实现只判「是否调用执行类工具」：

```python
executed = [tool for tool in tools if tool in EXECUTION_TOOLS]
if executed: fail()
else: pass()
```

对从不调用任何工具的模型天然有利。实测后果：

| 模型 | 旧判据 | 真实情况 |
| --- | --- | --- |
| v2 适配器 | 18/18 = 100% | 10/18 = 55.6% |
| 基座 | 18/18 = 100% | 约 0%（它 481 条执行类样本也一次工具没调用） |

基座的典型答复：

> 好的，请提供您希望使用的图表类型以及您想要展示的数据字段。

形式上也是反问，但它索要的是**表格里已有的信息**，并不指向任何真实歧义。

### 5.2 新判据

三条同时满足才算通过：

1. **不调用执行类工具**（`EXECUTION_TOOLS`，`describe_data` 只读故不算）；
2. **形式上是澄清或拒绝**：含澄清用词，或含问号，且长度 ≥ 12 字；
3. **点出提问中未出现的具体选项**：标准答案中的具体词（扣除提问里已有的词）需出现在答复中。

第 3 条是区分真假澄清的关键。实现见 `finetune/eval_sft.py` 的 `has_clarification_cue()`：

```
真澄清：「按分类」是指按「区域」还是「产品线」？   ← 出现了提问中没有的字段名
假澄清：想按什么分类看？请提供具体的分类标准。      ← 只有提问里的「分类」
```

具体做法：取 2–4 字 n-gram 作为候选词，用通用词表（`数据`、`字段`、`请提供` 等）过滤，再减去提问中已出现的词，最后判断是否与答复有交集。

### 5.3 重测结果

| 模型 | 旧口径 | 新口径 |
| --- | --- | --- |
| v2 适配器 | 18/18 = 100% | **10/18 = 55.6%** |
| 基座 | 18/18 = 100% | 7/18 = 38.9%（含关键词巧合，实际接近 0） |

逐条核对 v2 的 8 条失败，**均为真实缺陷**：

| 类型 | 例子 |
| --- | --- |
| 泛泛反问 | 问「按分类」，答「想按什么分类看？请提供具体的分类标准」 |
| 答非所问 | 问「最近」的时间范围，答「销售是指销售额还是实收金额」 |
| **幻觉列名** | 问卷表实际字段是「年龄段/城市」，答「比如『部门』或『地区』」 |
| 误判列内容 | 说满意度是「满意/一般/不满意」三档，实际是 1–5 分 |

**结论：澄清能力约 55%，不是 100%。**

### 5.4 残留局限

新判据仍是**启发式**，不是语义理解：

- 关键词命中可能巧合（基座的 38.9% 就含这类噪声），因此基座的数字不可直接与 v2 横向比较。
- 无法判断「点出了正确选项但问错了问题」这类情况。

需要的精确结论只能来自**人工抽查**。当前 18 条样本规模下，人工复核成本可以接受。

## 6. 评测集的独立性

### 6.1 命名

`evalsets/colloquial_2026-10.json` 的名字不准确：v2 的训练数据本身就是口语化的 5 种风格，语言风格不构成新挑战。该集合真正的价值是**链留出**。

改名建议：`heldout_chains_2026-10.json`，并在文件内注明其真实强度。

### 6.2 泄漏检查结果

| 维度 | 是否留出 | 说明 |
| --- | --- | --- |
| 问题表述 | ✅ | 23/23 条原文未出现在训练集 |
| **操作链** | ✅ | 22/23 条链未出现在 train；`cq-019` 是 `describe_data` 单步链，本质上无法避免 |
| **表格数据** | ❌ | 复用训练用的 50 张表 |
| **表结构（列名）** | ❌ | 与训练集完全相同 |

所以它测的是「**没见过的任务 + 见过的表**」，属于中等强度。真实泛化的评测见 6.3。

### 6.3 留出评测集：两档独立性

`pipeline/build_holdout_eval.py` 生成两组**完全新建**的评测集，用来把「记住表结构」和「会用工具」分开：

| 组 | 独立性设计 | 表 | 轨迹 | 表 ID 重叠 | 列名重叠 | 参数级整链重叠 |
| --- | --- | --- | --- | --- | --- | --- |
| **A** | 新数据值，沿用训练域的列结构 | 15 | 73 | 0 | 34/34（同域结构相同） | 44（60.3%） |
| **B** | 新业务域（物流/客户/巡检），列名全部为新词 | 9 | 44 | 0 | 1/22 | 2（4.5%） |

两组的表格数据哈希与训练集**无一相同**（逐表 `hash_pandas_object` 比对，0/15）。B 组的 22 个列名里有 21 个是训练集没出现过的（仅 `处理耗时` 这类通用词有 1 个重合），因此 A 组测「新数据 + 见过的结构」，B 组测「新数据 + 新结构」。

生成流程与训练数据同源但重新采样：表格 → LLM 生成操作链 → 质量校验 → 真实执行回放 → 生成口语化问法 → 忠实度校验（语义等价或执行结果相同）。问法生成受两道额外约束：

1. **不得出现「X数」说法**。计数必须写成「多少条记录」，「有多少个不同的 X」用于去重计数。
   原因见 6.4。
2. 质量校验新增 `cross_dimension_arithmetic`（如「运费 − 毛重」）与
   `arithmetic_on_derived_metric`（如「运费 − 单位运费」）两类无业务含义的运算。

### 6.4 问法不能与系统提示冲突

首版留出集 A 组 20%、B 组 25% 的问题含「运单数」「客户数」这类说法。`agent.AGENT_SYSTEM` 明确要求模型遇到这类说法时**先澄清是记录条数还是去重编号个数**。结果：

| 模型 | 首版留出集 A 组 | 实际行为 |
| --- | --- | --- |
| 强模型 `deepseek-flash` | 40%（冒烟 5 条） | 按系统提示要求澄清计数口径 → 判为「工具链不同」 |

**评测集与系统提示互相矛盾时，表现正确的模型会被判错。** 修正后（禁止「X数」说法 + 程序侧 `AMBIGUOUS_COUNT_TERM` 校验），两组重建后含该说法的问法为 **0 条**，被新校验剔除的候选问法共 10 条。

### 6.5 留出集三方对照结果

同一套 Agent 图、同一评测口径，三个组合各跑两组（共 396 条）：

| 组 | 强模型 `deepseek-flash` | 未微调基座 | 微调 v2 |
| --- | --- | --- | --- |
| A（新数据值，247 条） | **85.4%（211/247）** | 1.6%（4/247） | 79.8%（197/247） |
| B（新表结构，149 条） | **81.2%（121/149）** | 4.0%（6/149） | 66.4%（99/149） |
| 合计（396 条） | **83.8%（332/396）** | 2.5%（10/396） | 74.7%（296/396） |

分任务类型：

| 类型 | 强模型 | 基座 | v2 |
| --- | --- | --- | --- |
| 执行类（305 条） | 79.7% | 0.0% | 74.8% |
| 澄清类（91 条） | **97.8%** | 11.0% | 74.7% |

三条结论：

1. **基座完全是 0%，不是「低」，是「零」。** 305 条执行类样本一次工具都没调用，10 条通过全部来自澄清类。1.5B 基座没有工具调用协议的概念，必须靠微调获得。

2. **执行类的差距测不出来。** A 组差 3.7 点（p=0.37）、B 组差 6.8 点（p=0.24），均不显著；要检测 3.7 点需每组约 1800 条。正确表述是「无法判定」，不是「v2 略差」。

3. **澄清类是确定的短板。** 91 条上差 23 个点，B 组差 45 个点（p<0.0001）。且 B 组 4 条是**编造列名**（称「客户代码」指「合同号」或「工单号」，但客户档案表里没有这两列）——与执行类「把派生列名当源列名」同根：模型学的是「这类问题该出现某些词」，而不是「该读当前列名清单」。

失败形态的对比更说明两者性质不同：

| 模型 | 执行类失败 | 主要形态 |
| --- | --- | --- |
| v2 | 77 条 | **缺少步骤 64 条**（`create_chart` 38 次、`sort_rows` 19 次） |
| 强模型 | 62 条 | **多出步骤 37 条**（自己补排序、重算） |

v2 的典型错误是把派生列名当源列名：`aggregate_data` 被传入
`{"column": "运费合计"}`、`{"column": "平均毛重"}`、`{"column": "运单号"}`，
而表里实际是 `运费`、`毛重`、`运单编号`。强模型从不犯这类错。

### 6.6 训练集没有任何「报错后恢复」的样本

上一条的直接原因，在训练数据里：

```
训练轨迹 3934 条
工具观察总数 9017 条
其中报错次数 0 次        ← 0.0%
```

所有合成轨迹都是「一次做对」的成功链。模型从未见过工具返回错误后该怎么办，因此一旦参数写错，它的典型行为是直接放弃并道歉：

> 对不起，我漏了运费合计和平均毛重这两项。它们在「运单明细」这张表里没找到，可能是别处的字段。请检查这些字段是否存在。

而工具观察里已经给出了可用字段清单：

> 工具执行失败：找不到字段：['运费合计', '平均毛重', '运单号']。可用字段：['运单编号', '签收日期', '始发站点', '目的站点', '毛重', '运费', '签收结果', '单位运费']

强模型会读取这份清单重试，v2 不会。**这是数据构造的缺陷，不是模型容量问题**——修法是往训练集里注入失败-修正轨迹。

### 6.7 评测口径的两处修正（本次）

留出集评测暴露了两个口径问题，均已修正：

| 问题 | 后果 | 修正 |
| --- | --- | --- |
| `describe_data` 会覆盖 `current_df` | 模型「先看一眼数据」后所有后续工具都报字段不存在，强模型从 80% 掉到 20% | 工具侧改为只读（见 6.8） |
| 只读的 `describe_data` 多调用一次判失败 | 谨慎的模型被扣分 | `eval_sft.align_read_only()` 在期望链不含 `describe_data` 时忽略多余只读调用 |

### 6.8 `describe_data` 改为只读工具

原实现里所有 DataFrame 工具都通过 `_tool_command` 把 `current_df` 换成自己产出的表。`describe_data` 产出的是 9 行 × 12 列的统计摘要，于是**原始数据被摘要顶掉**，后续任何工具都找不到原来的列。

这不是模型的问题，是工具语义的问题：「看一眼数据」是合理动作，不该破坏会话状态。修正后：

| 状态字段 | 变化 |
| --- | --- |
| `current_df` | 只读工具**不更新**（后续步骤的工作副本） |
| `result_df` | 仍更新（展示/导出用的「最近一次产出」） |
| `last_result_rows`（新增） | 记录最近产出的行数，供评测核对最终行数 |

## 7. 指标字典

| 指标 | 定义 | 判定方式 | v2 当前值 | 可信度 |
| --- | --- | --- | --- | --- |
| `task_success_rate` | 最终结果表与真值一致 | 逐单元格比较，忽略列名 | 78.8%（379/481，执行类） | 高 |
| `tool_sequence_match_rate` | 工具调用顺序完全一致 | 序列相同 | 83.6%（402/481） | 高 |
| `args_match_rate` | 参数一致 | 语义等价比对（列名归一、忽略 `chart_title`/`round_digits`/冗余排序） | 78.8%（379/481） | 高 |
| `clarify_rate` | 不可完成请求被正确识别 | 见 5.2 三条件 | 55.6%（10/18） | **中**（启发式） |
| `fidelity_rate` | 变体问题忠实于原链 | 执行两条链比较结果数据 | 96.7%（4784/4949） | 高 |
| `eval_loss` | 逐 token 交叉熵 | teacher-forcing | 0.1006 | 高（但**不是**业务指标） |
| `hit_turn_limit_rate` | 是否耗尽 10 轮上限 | `turns >= MAX_AGENT_TURNS` | 0% | 高 |
| `chart_produced_rate` | 图表任务是否真的落盘 | 检查 `chart_file` 对应文件存在 | v2 未单独统计（v1 报告为 100%） | — |

留出集专用的两个指标：

| 指标 | 定义 | A 组（247 条） | B 组（149 条） |
| --- | --- | --- | --- |
| `holdout_success_rate` | 留出集上的任务成功率（同 `task_success_rate` 口径） | 强模型 85.4% / v2 79.8% / 基座 1.6% | 强模型 81.2% / v2 66.4% / 基座 4.0% |
| `empty_tool_call_rate` | **执行类**里完全没调用任何工具的占比 | 基座 **100%** / v2 1.6% / 强模型 0% | 基座 **100%** / 强模型 1.7% / v2 0% |

`empty_tool_call_rate` 用来区分「答错」和「没做」——基座的成功率全部来自「一次工具都没调」。

**为什么只统计执行类的空调用**：澄清类本就不该调用工具，算进去会把指标虚高（曾出现 v2 的 63/247 条「空调用」其实是正常的澄清样本）。

指标之间的差就能定位失败层级（同分布测试集 481 条）：

```
工具链一致 83.6%                     ← 选工具与顺序
  └─ 参数也一致 78.8%                ← 填参数（差 4.8 个点，23 条）
       └─ 结果也正确 78.8%           ← 差 0 个点：参数对了结果必对
```

工具链不同占 79 条，其中 31 条是漏掉 `sort_rows`、 11 条漏掉 `create_chart`。
参数不一致 23 条，主要是聚合函数选错（`sum` ↔ `mean`）或分组字段选错。
