# LoRA 微调实验记录

> **最新结果请看 [post-training-report.md](./post-training-report.md)**：本文件为历史过程记录，其中 3.1–3.2 的部分数字已被 396 条留出集的测量取代。

记录 `Qwen2.5-1.5B-Instruct` 在本项目 Excel Agent 任务上的两轮微调实验：数据构造、训练配置、评测结果，以及从失败中提炼的结论。

硬件基准：RTX 3050（6 GB），4-bit QLoRA，`batch=1 × 梯度累积 8`。

## 1. 两版数据对照

| 维度 | v1（规则链） | v2（LLM 链 + 口语化） |
| --- | --- | --- |
| 操作链来源 | 规则枚举（列 × 操作 × 参数） | 100% LLM 生成，逐条校验 |
| 独立链数 | 600 | 1000 |
| 问法 | 7 个模板句式 + 程序拼装的 summary | 5 种风格（plain/minimal/business/verbose/no_sheet） |
| 澄清样本 | 无 | 147 条（8 类歧义） |
| 训练样本 | 1200 | 3934 |
| 步数分布 | 1 步 292 / 2 步 203 / 3 步 40 | 1 步 225 / 2 步 1990 / 3 步 1604 |
| `max_length` | 4608 | 5184 |

v2 的多步样本占比从 20% 提升到 **94%**，因为规则生成器穷举时偏向简单链，而 LLM 更倾向产出有业务意义的组合。

## 2. 训练结果

| 指标 | v1 | v2 |
| --- | --- | --- |
| 训练步数 | 360 | 492 |
| 耗时 | 2 小时 59 分 | 5 小时 04 分 |
| train_loss | 0.156 | 1.247 |
| eval_loss | 0.0029 | 0.1006 |
| 可训练参数 | 18.5 M（1.18%） | 同左 |

**`eval_loss` 不能跨数据集横向比较。** v1 的 0.0029 是模板数据的假象：同一操作链只有 2 条句式，模型几乎是把固定串背下来。v2 的 0.1006 对应真实口语的多样性，才是有意义的难度指标。

判断训练是否健康，看 train_loss 的下降形态而不是绝对值：v1 从 6.38 降到 0.0004（25 步内就到 0.08），v2 从 7.79 降到 0.67（末段在 0.67–0.9 波动）。v1 收敛得太快，正是「一句话对应一个固定串」的表现；v2 的波动说明模型仍在学习，没有塌缩到复读。

上述 3.1–3.3 的数字都建立在「见过的表」上。为把「记住表结构」和「会用工具」分开，另建两组完全独立的评测集（生成方式与独立性核查见 [eval-protocol.md](./eval-protocol.md) 6.3–6.4）：

| 组 | 设计 | 表 | 轨迹 |
| --- | --- | --- | --- |
| A | 新数据值，沿用训练域的列结构 | 15 | 73 |
| B | 新业务域（物流 / 客户 / 巡检），列名基本全新 | 9 | 44 |

三个组合在同一 Agent 图、同一评测口径下的结果：

| 组 | 强模型 `deepseek-flash` | 未微调基座 | 微调 v2 |
| --- | --- | --- | --- |
| A（新数据值） | 65.8%（48/73） | **0.0%（0/73）** | **89.0%（65/73）** |
| B（新表结构） | 63.6%（28/44） | **0.0%（0/44）** | **68.2%（30/44）** |
| 合计（117 条） | 65.0%（76/117） | 0.0%（0/117） | **81.2%（95/117）** |

**基座不是「低」，是「零」**：117/117 条一次工具都没调用，全部以文字回答或索要本就已知的信息。典型答复：

> 好的，请提供需要去重的列的名称。

而提示里已经给出了完整列名清单。1.5B 基座没有工具调用协议的概念，必须靠微调获得。这一结论在 396 条上同样成立（305/305 条执行类零工具调用）。

**v2 的优势高度依赖表结构是否见过**：

| 组 | v2 | 强模型 | 差值 | 该组与训练集的关系 |
| --- | --- | --- | --- | --- |
| A | 89.0% | 65.8% | **v2 +23.2** | 列名 34/34 完全相同，参数级整链重叠 60.3% |
| B | 68.2% | 63.6% | v2 +4.6 | 列名仅 1/22 重合，参数级整链重叠 4.5% |

换成新列名后，19 个百分点的领先缩小到 4.6 个百分点。**微调带来的收益大部分来自记住训练域的表结构，而不是可迁移的工具使用能力。**

失败形态也印证这一点：

| 模型 | 组 | 失败数 | 「字段找不到」类自述失败 |
| --- | --- | --- | --- |
| v2 | A | 8 | 4（50%） |
| v2 | B | 14 | **10（71%）** |
| 强模型 | A | 25 | 0 |
| 强模型 | B | 16 | 0 |

v2 的典型错误是把派生列名当源列名：

```
问题：按始发站点汇总：运费合计、平均毛重、每个站点多少条记录……
实际：aggregate_data({"group_by":["始发站点"],
      "metrics":[{"column":"运费合计","function":"sum"},
                 {"column":"平均毛重","function":"mean"},
                 {"column":"运单号","function":"count"}]})
表里实际字段：运单编号、签收日期、始发站点、目的站点、毛重、运费、签收结果、单位运费
```

`运费合计`、`平均毛重`、`运单号` 三个列名全错。强模型从不犯这类错，它的失败形态是多余步骤、漏步骤、参数口径不一致。

## 4. 失败模式分析

v2 在同分布测试集上失败 102 条：

| 模式 | 条数 |
| --- | --- |
| **缺少 `sort_rows`** | **31** |
| 参数不一致（工具链相同） | 23 |
| 未调用工具 | 12 |
| 缺少 `create_chart` | 11 |
| 其他（多出步骤、换工具） | 25 |

### 4.1 排序步骤被系统性省略

典型样本：

```
问：按科目汇总，算平均差异和实际支出合计，然后按平均差异从高到低排
期望：aggregate_data → sort_rows
实际：aggregate_data
```

这不是随机错误，而是**训练目标与任务语义脱节**的必然结果：

- SFT 优化的是逐 token 似然。「少写一步 `sort_rows`」在 loss 上的代价，远小于「字段名写错」。
- 排序只改变行顺序，不改变行数与列名。在按结果表比较的评测里，它却是决定性的。

绘图缺失只有 11 条，因为 `create_chart` 会改变 `chart_file` 状态，跳过它的下游影响更明显。换句话说，**越是没有"副作用"的必要步骤，越容易被模型省略**。

单靠增加同类样本量能缓解，但治本的做法是：
- 在评测里把排序/绘图设为强约束（本项目已这样做）；
- 或引入偏好优化（DPO），对「看似合理但实质错误」的轨迹给出惩罚。

### 4.2 参数错误

23 条工具链正确但参数不符。典型是聚合函数选错（`sum` ↔ `mean`）或分组字段选错，而非语法错误。这类问题与问法歧义相关（见 4.4）。

### 4.3 不可完成请求仍会硬套工具

口语化评测集的 9 条不可完成请求里，v2 仍有 3 条强行调用：

| 请求 | 实际行为 |
| --- | --- |
| 满意度低于 3 的行标红 | `filter_rows` |
| 画出销售额的 7 天移动平均趋势 | `create_chart` |
| 插入一个公式列自动算 | `add_computed_column` |

共同点是**工具名与请求字面高度相似**。模型学到了「提到"标红"就找筛选」，却没有「工具不能做格式设置」的概念。

### 4.4 计数口径歧义（已在数据侧修正）

早期分析中有一类"模型总选错列"的失败：

```
链：aggregate_data(metrics=[nunique(订单号) as "订单数"])
问：按销售员汇总销售额合计和订单数
解析：count(订单号)
```

根因在工具语义，不在模型：`count` 原本是 `Series.count()`（该列非空值个数），因此「有多少条反馈」会因模型选了哪一列而得到不同答案，而用户无从知晓该指定哪一列。

已改为 **`count` = 组内行数**（pandas `"size"`），`nunique` 保持原语义。这样同一个「有多少条」无论引用哪一列都得到相同结果。相关说明见 [dataset-plan.md](./dataset-plan.md) 第 1 节。

## 5. 歧义澄清能力

v2 新增 8 类可验证歧义检测（`dataset_builder/ambiguity.py`），在 50 张表上检出 303 个场景：

| 类型 | 触发条件 | 检出 |
| --- | --- | --- |
| `metric_column` | 同域两个数值列（单价/销售额、工时/加班时长） | 50 |
| `group_dimension` | ≥2 个分类列（"按分类"指哪个） | 50 |
| `top_n` | "最多的几个"未给条数 | 50 |
| `chart_type` | "画个图"未说图表类型 | 50 |
| `missing_value` | 数值列有空值，平均值是否忽略 | 45 |
| `time_range` | 日期跨 >30 天，"最近"边界不清 | 30 |
| `count_semantics` | **去重数 ≠ 行数**时才成立 | 18 |
| `aggregation` | 量表列求和 vs 平均 | 10 |

关键设计是**歧义必须可验证**：`count_semantics` 只在去重数不等于行数时生成。此前用 30 条"订单数"样本，其中 8/9 的链因为订单号恰好唯一而 `nunique == count`，两种理解结果相同——对这种样本反问用户是多余的打扰。

训练效果：

| 指标 | v2 |
| --- | --- |
| 澄清类样本（18 条） | **100%** |
| 抽样 40 条的执行类 | 70%（其中工具链错误 10） |

澄清样本占比控制在训练集 **2.9%**。过高会让模型对什么都说"请补充信息"，这比猜错更烦人。

### 6.1 错误恢复缺口是留出集失败的主因

留出集 B 组上 v2 失败 14 条，其中 **10 条（71%）是自述「字段找不到」**。逐条追踪后确认，训练数据的构成直接决定了这个失败：

```
训练轨迹     3934 条
工具观察     9017 条
其中报错次数 0 次        ← 0.0%
报错后继续调用的轨迹 0 条
```

所有合成轨迹都是「一次做对」的成功链，模型从未见过工具返回错误后的样子。而工具其实已经把恢复所需的全部信息给了出来：

> 工具执行失败：找不到字段：['运费合计', '平均毛重', '运单号']。可用字段：['运单编号', '签收日期', '始发站点', '目的站点', '毛重', '运费', '签收结果', '单位运费']

v2 的处理是放弃并道歉：

> 对不起，我漏了运费合计和平均毛重这两项。它们在「运单明细」这张表里没找到，可能是别处的字段。请检查这些字段是否存在。

强模型会读这份清单、改写参数、重试。**这是数据构造的缺陷，不是模型容量问题。**

修法：在数据流水线里主动注入失败-修正轨迹。具体做法是生成链后人为把某些列名替换成近似但不存在的名字（`运费` → `运费合计`），真实执行拿到报错，再从报错信息恢复，把「报错 → 恢复」两轮都写进轨迹。这样模型能学会两件事：一是从错误信息里提取可用字段，二是**不要在答复里声称做了没做的事**（v2 现在存在「柱状图也画好了」但实际没调用 `create_chart` 的幻觉）。

## 7. 工程注意事项

这些是实际踩过的坑，对后续训练仍有价值。

### 7.1 损失掩码必须自己算

Qwen2.5 的 chat template 不含 `{% generation %}` 标记，`apply_chat_template(..., return_assistant_tokens_mask=True)` 会返回 `None`。若此时退化为「整段都算损失」，模型会去学习复述工作表概况与工具输出——这是微调最常见的失败方式。

`finetune/train_lora.py` 改为按消息前缀增量编码，逐个求出 assistant 片段的 token 区间。实测一条样本 3941 token 中只有 185 个参与损失（4.7%）。

### 7.2 `max_length` 必须覆盖 assistant 尾部

训练样本的提示部分（数据概况 + 8 行预览）约 2680 token，完整轨迹 p50 3810、max 5181。用 2048 会把**所有** assistant 标签截掉，等于训练「复述提示」；用 4608 仍有 5.3% 样本被截断，被截断的样本只学工具调用、不学汇报。

最终取 5184，零截断。

### 7.3 显存优化：只对监督位置算 logits

因果 LM 默认对整段序列做 `lm_head` 投影。词表 151936 × 序列 3941 token，仅 logits 就占约 2.4 GB，反向传播还要一份，6 GB 显卡会溢出到共享内存。

利用 `logits_to_keep` 的布尔掩码只投影监督位置（约 5%），峰值显存从 **9.93 GB 降到 2.40 GB**，loss 完全一致。

### 7.4 检查点策略

单 epoch 训练动辄数小时。`save_strategy="epoch"` 意味着中断后一无所有（v2 实验第一次尝试在第 10 步被中断，未产出任何文件）。现改为按步保存（`--save-every 4`，每个 epoch 存 4 次）。

### 7.5 transformers 版本差异

`transformers 5.x` 移除了 `TrainingArguments(warmup_ratio=...)`，只能用 `warmup_steps`。脚本已改为按总步数换算，并支持 `--warmup-steps` 直接指定。

## 8. 数据质量校验的教训

### 8.1 参数比对只能近似，最终判据是执行结果

早期用「规范化后参数相等」判断变体是否忠实，把大量**结果完全相同**的链判为错误：

```
期望：aggregate_data(metrics=[{column: 预算金额, function: sum, name: 预算合计}])
解析：aggregate_data(metrics=[{column: 预算金额, function: sum}])   ← 省略 name
      create_chart(chart_y="预算金额_sum")                          ← 代码自动拼名
```

两者执行结果一致，只是列名文字不同。这类误判曾达 2412 条，使忠实度从 93.2% 被低估到 44.5%。

改为「执行两条链、比较结果数据」后忠实度为 **96.7%**。比对器仍保留参数级的快速路径，但最终裁决必须落到数据上。

### 8.2 过滤规则要区分「内部标识」与「业务用语」

LLM 生成的列名是「销售额合计」「平均满意度」这类自然业务用语，用户完全可能说出来；只有含下划线的 `销售额_sum`、`预算金额_x_差异` 才是程序内部命名。最初把两者都当泄漏，误杀 2494 条变体（通过率仅 49.9%），修正后为 99.0%。

## 9. 当前能力结论

> 本节已按 396 条留出集更新。旧版此处曾写「歧义澄清 100%」——那是旧判据的假象，
> 旧判据只检查「是否调用执行类工具」，对从不调用工具的模型天然有利。

| 能力 | 状态 |
| --- | --- |
| 单步工具使用 | ✅ 100%（强模型同口径 61.9%/42.9%） |
| 口语化理解 | ✅ 31.2% → 71.9% |
| 见过的表结构上的执行 | ✅ 79.8%（留出集 A） |
| 没见过的表结构上的执行 | ⚠️ 66.4%（留出集 B），弱于强模型 81.2% |
| 歧义澄清 | ⚠️ 74.7%（91 条），弱于强模型 97.8% |
| 2–3 步链 | ⚠️ 漏掉末尾步骤：`create_chart` 38 次、`sort_rows` 19 次 |
| 工具报错后恢复 | ❌ 0% 训练样本，遇到字段错就直接放弃 |
| 失败时如实汇报 | ❌ 9 条未调用画图却说「柱状图也画好了」 |
| 4 步以上长链 | ❌ 未训练 |

一句话定位：**v2 学会了工具协议，但把「该用哪些列名」也一起记成了模式。** 前者可迁移，后者不可。

## 11. 复现

数据构造脚本位于 `pipeline/`，产物统一写入 `build/`（该目录被 `.gitignore` 忽略，因此只有输入脚本入库）。

```powershell
# 1. 生成链池（纯 LLM，1000 条）
python pipeline/prepare_chains.py --no-rule --llm-target 1000 --llm-rounds 3

# 2. 生成口语化变体（5 种风格）
python pipeline/generate_variants.py --count 5 --out build/variants.json

# 3. 忠实度校验（并发 8，反向解析每条变体）
python pipeline/verify_all_variants.py --workers 8

# 4. 用执行结果裁决，产出忠实集
python pipeline/verify_by_execution.py

# 5. 生成歧义澄清样本
python pipeline/make_ambiguity_dataset.py --per-kind 1

# 6. 转 SFT 轨迹（澄清样本按 3% 上限抽样）
python pipeline/variants_to_sft.py --variants build/variants-faithful-v2.json `
  --no-templates --clarifications build/clarifications.json --out build/sft-expanded

# 7. 训练
python finetune/train_lora.py --data build/sft-expanded `
  --model models/Qwen2.5-1.5B-Instruct --output build/lora-expanded `
  --epochs 1 --max-length 5184 --save-every 4

# 8. 评测
python finetune/evaluate_colloquial.py --set evalsets/colloquial_2026-10.json `
  --adapter build/lora-expanded
python finetune/eval_sft.py --split test --adapter build/lora-expanded
```

第 1、2、3 步会调用远程模型；如需先小样验证措辞质量：

```powershell
python pipeline/trial_variants.py survey-20251078 --count 4      # 单表 12 条链
python pipeline/verify_variants.py                              # 校验该小样
```
