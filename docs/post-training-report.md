# 后训练微调实验报告（v2 版）

**报告日期**：2026-11-04
**实验对象**：Qwen2.5-1.5B-Instruct + QLoRA 适配器（v2）
**报告范围**：训练数据构造 → LoRA 训练 → 独立留出集评测 → 三方对照 → 失败分析

---

## 摘要

在 3934 条自建 Agent 轨迹上对 1.5B 基座做 QLoRA 微调（1 epoch、492 步、约 5 小时），随后在 396 条**完全独立**的留出集上与强模型（`deepseek-flash`）和未微调基座做三方对照。

**核心结论**：

1. **微调是必要的**：基座 2.5% → v2 74.7%，工具调用能力从「完全没有」到「基本可用」。基座在 305 条执行类样本上**一次工具都没调用**。
2. **v2 在歧义澄清上明显弱于强模型**（91 条：74.7% vs 97.8%），这是两组对比中统计显著的差距。
3. **v2 在执行类上与强模型无统计显著差异**。但这不等于「相当」——现有样本量不足以判定 3.7 个点的差异（需每组约 1800 条，现有 187 条）。
4. **两模型失败形态相反**：v2 是「漏步骤」（64 条），强模型是「多步骤」（37 条）。v2 漏的主要是 `create_chart`（38 次）和 `sort_rows`（19 次）。
5. **发现并修复了训练/推理的观察文本不一致**（P0），但 **v3 尚未训练**，修复效果未经验证。

## 1. 实验设置

### 1.1 三个对照组

三者是**同一基座 + 不同适配器**，不是三个独立模型：

| 名称 | 构成 | 说明 |
| --- | --- | --- |
| 强模型 | `deepseek-flash`（远程 API） | 业务能力上限参照 |
| 未微调基座 | `Qwen2.5-1.5B-Instruct` 原始权重 | 能力下限 |
| 微调 v2 | 基座 + `build/lora-expanded` | 本次实验产物 |

### 1.2 评测集：两档独立性，共 396 条

| 组 | 设计目标 | 表 | 执行类 | 澄清类 | 合计 |
| --- | --- | --- | --- | --- | --- |
| **A** | 新数据值，沿用训练域列结构 | 30 | 187 | 60 | **247** |
| **B** | 新业务域（物流/客户/巡检），列名基本全新 | 18 | 118 | 31 | **149** |

独立性核查：

| 维度 | A 组 | B 组 |
| --- | --- | --- |
| 表 ID 与训练集重叠 | 0 / 30 | 0 / 18 |
| 表数据哈希与训练集相同 | 0 / 30 | 0 / 18 |
| 列名与训练集重叠 | 34 / 34（结构相同） | 1 / 22 |
| 轨迹与训练集完全重复 | 0 / 247 | 0 / 149 |

**分组的意义**：A 组测「换了数据值还会不会」，B 组测「换了表结构和业务词汇还会不会」。只测 A 组会把「记住表结构」误判成能力。

### 1.3 判定口径

**执行类**，三种情况任一通过：
1. 工具链与标准答案一致（参数允许列名别名等等价写法）
2. 做法不同，但真实执行出的结果表与标准答案等价
3. 等价的定义：行列数一致、单元格取值一致；允许行顺序不同、列名不同（按列位置比较）

不通过：「一次工具都没调用」（答案只能靠猜）、「期望画图但没画」、「有调用但全部失败」。

**澄清类**，只判理由是否成立：
- 必须点出提问中未出现的**具体选项**，或点名表里真实存在、提问未提到的**字段**
- 索要提示里已给出的信息（列名、表头、数据范围）**不算**澄清
- 先只读查看再反问，同样成立

## 2. 训练数据

### 2.1 规模与构成

| 分区 | 样本数 | 其中多步链 |
| --- | --- | --- |
| train | 3934 | 3594 |
| val | 498 | 460 |
| test | 499 | 456 |
| 合计 | 4931 | — |

数据来源链：LLM 生成操作链 1000 条 → 口语化变体 4664 条 → 忠实度校验 → 3934 条 SFT 轨迹 + 147 条澄清样本（train 分区 115 条）。

### 2.2 轨迹格式

每条样本展开为与线上完全一致的交互序列：

```
system(AGENT_SYSTEM)
  → user(工作表数据概况 + 问题)
  → assistant(tool_call) → tool(观察结果)
  → assistant(tool_call) → tool(观察结果)
  → assistant(最终答复)
```

### 2.3 中间结果表确实进入了训练输入

这是本次复查的重点。**9017 条工具观察全部含真实数据**，不是编造的：

```
操作成功。当前结果为 10 行 × 3 列。
字段：['月份', '预算合计', '平均实际支出']
样例：
     月份      预算合计       平均实际支出
2025-06 144228.68 65150.163333
...（最多 8 行）
```

构成分布：

| 观察类型 | 条数 |
| --- | --- |
| `create_chart`（图表成功措辞） | 1168 |
| `describe_data`（只读措辞） | 512 |
| 其余数据框工具（结果预览） | 7337 |
| **合计** | **9017** |

**重要限定**：观察只含**前 8 行**预览（`max_colwidth=40`）。模型能看见列名与结构，看不见第 9 行之后的数值。因此它不能靠「读数据」回答，只能靠工具计算——这是设计取向，也意味着需要「看全表」的任务无法完成。

**观察不参与损失**：`train_lora.py` 只对 `role == assistant` 打监督标记，tool 观察的 labels 全为 `-100`。它是上下文，不是监督目标。

### 2.4 数据长度与截断

| 项 | 数值 |
| --- | --- |
| 最长序列 | 5217 token |
| `max_length` 默认值 | 5376 |
| 截断样本数（4931 条全量实测） | 0 |

历史教训：用 2048 会截掉全部 assistant 标签（模型只学复述提示）；用 4608 仍有 5.3% 样本被截断（被截断样本只学工具调用、不学汇报）。本次已把默认值提到 5376 并加测试锁定下限。

## 3. 训练过程

### 3.1 超参数

| 项 | 值 |
| --- | --- |
| 量化 | 4-bit QLoRA（nf4、bf16 计算、双重量化） |
| batch size × 梯度累积 | 1 × 8（等效 8） |
| 学习率 | 1e-4，cosine 退火 |
| 预热 | 14 步 |
| epochs | 1 |
| 总步数 | 492 |
| 耗时 | 1.828e4 秒 ≈ **5 小时 5 分** |
| 硬件 | RTX 3050 6GB |

### 3.2 收敛情况

| epoch 区间 | train loss 均值 |
| --- | --- |
| 0.01 – 0.19 | 2.5527 |
| 0.20 – 0.39 | 1.1668 |
| 0.40 – 0.58 | 0.9354 |
| 0.59 – 0.77 | 0.8536 |
| 0.78 – 1.00 | 0.8046 |

`train_loss` 最终 1.247，`eval_loss` 0.1006。

**判断**：loss 仍在下降，学习率已退火到 ~0（末步 9.7e-09）。即当前配置下 1 轮已到极限，但**不代表模型已充分收敛**。

**`eval_loss` 不能当准确率**：0.1006 表示 teacher-forcing 下逐 token 预测很准；自由运行 Agent 时每步依赖自己的上一步输出，实测任务成功率只有 74.7%。两者不可互换。

## 4. 评测结果

### 4.1 总体

| 组 | 强模型 | 基座 | v2 |
| --- | --- | --- | --- |
| A（247 条） | **85.4%**（211） | 1.6%（4） | 79.8%（197） |
| B（149 条） | **81.2%**（121） | 4.0%（6） | 66.4%（99） |
| 合计（396 条） | **83.8%**（332） | 2.5%（10） | 74.7%（296） |

### 4.2 分会话类型

**执行类（305 条）**

| 组 | 强模型 | 基座 | v2 |
| --- | --- | --- | --- |
| A（187） | 81.8% | 0.0% | 78.1% |
| B（118） | 76.3% | 0.0% | 69.5% |
| 合计 | **79.7%** | 0.0% | **74.8%** |

**澄清类（91 条）**

| 组 | 强模型 | 基座 | v2 |
| --- | --- | --- | --- |
| A（60） | 96.7% | 6.7% | 85.0% |
| B（31） | **100.0%** | 19.4% | **54.8%** |
| 合计 | **97.8%** | 11.0% | **74.7%** |

### 4.3 按期望步数（执行类）

| 组 | 模型 | 1 步 | 2 步 | 3 步 |
| --- | --- | --- | --- | --- |
| A | 强模型 | 61.9% | 88.4% | 75.9% |
| A | v2 | **100.0%** | 72.3% | **81.5%** |
| B | 强模型 | 42.9% | 79.5% | 75.0% |
| B | v2 | **100.0%** | 60.2% | **89.3%** |

两个反常现象，都经核实为真实：

- **v2 单步任务 100%，强模型只有 61.9%/42.9%**。原因是强模型**多做了一步**——调完 `describe_data` 又用 `aggregate_data` 重算一遍，结果表变成聚合结果而非统计摘要。
- **v2 的 3 步任务反而好于 2 步**。2 步任务多为「单步 + 追加画图/排序」，而追加步骤正是 v2 最易漏的。

## 5. 统计显著性与测试集功效

| 对比 | 差值 | p 值 | 结论 |
| --- | --- | --- | --- |
| A 总分 | +5.6 点 | 0.0967 | **不显著** |
| B 总分 | +14.8 点 | 0.0037 | 显著 |
| A 执行类 | +3.7 点 | 0.3660 | **不显著** |
| B 执行类 | +6.8 点 | 0.2415 | **不显著** |
| A 澄清类 | +11.7 点 | 0.0268 | 显著 |
| B 澄清类 | +45.2 点 | <0.0001 | 显著 |

**检测不同效应量所需样本量**（每组，α=0.05，功效 0.8）：

| 目标 | 所需条数 | 现有 |
| --- | --- | --- |
| A 执行类 3.7 点 | 1795 | 187 |
| B 执行类 6.8 点 | 674 | 118 |
| 假设 5 点 | 1023 | — |
| 假设 10 点 | 277 | — |

**结论**：

- 「v2 执行能力弱于强模型」——**现有数据无法支持，也无法否定**。正确表述是「测不出来」。
- 「v2 澄清能力弱于强模型」——数据充分，B 组差 45 个点，p<0.0001。
- 396 条总量看起来够，但拆到执行类只有 118–187 条，功效不足。

## 6. 失败分析

### 6.1 形态：v2 会「漏」，强模型会「多」

执行类失败分布：

| 形态 | 强 A | 强 B | v2 A | v2 B |
| --- | --- | --- | --- | --- |
| 一次工具都没调 | 0 | 2 | 3 | 0 |
| **多出步骤** | **21** | **16** | 0 | 4 |
| **缺少步骤** | 1 | 0 | **36** | **28** |
| 换用别的工具 | 0 | 0 | 0 | 2 |
| 链相同但结果不同 | 9 | 7 | 2 | 2 |
| 最终行数不同 | 0 | 1 | 0 | 0 |
| 其他 | 3 | 2 | 0 | 0 |
| 失败合计 | 34 | 28 | 41 | 36 |

### 6.2 v2 漏掉的具体工具

按「实际步骤数 < 期望步骤数」统计（A 39 条、B 28 条）：

| 缺失工具 | A | B | 合计 |
| --- | --- | --- | --- |
| `create_chart` | 23 | 15 | **38** |
| `sort_rows` | 13 | 6 | **19** |
| `top_n_rows` | 4 | 6 | 10 |
| `aggregate_data` | 5 | 2 | 7 |
| `describe_data` | 5 | 1 | 6 |
| `filter_rows` | 1 | 0 | 1 |

且**多数只差最后一步**：A 组 27/39、B 组 26/28 都只缺一个步骤。

对比 4.3 节：以 `create_chart` 结尾的样本 v2 通过率 **50.0%**，而 `sort_rows` 79.7%、`top_n_rows` 86.2%。

### 6.3 v2 会在没做成时声称完成

9 条样本（A 3 + B 6）在**未调用 `create_chart`** 的情况下声称已画图：

> 问：按仓库汇总库存数量合计和安全库存合计，再统计每个仓库有多少条记录，然后画个柱状图…
> 实际调用：`aggregate_data`
> 答复：「……按你的要求做完了，一共 4 列：仓库、库存总量、安全库存总量、记录数。**柱状图也画好了**，可以直接比较各仓库的库存总量。」

同一条答复开头还写着「对不起，我漏看「记录数」这个字段」——它**知道有字段没对上，仍声称完成**。

### 6.4 v2 的澄清缺陷

B 组 14 条澄清失败，逐条人工核对：

| 形态 | 条数 | 例子 |
| --- | --- | --- |
| 泛泛反问，不点名选项 | 6 | 「想按什么分类看？请提供具体的分类标准」 |
| **编造列名** | 4 | 「『客户代码』是指『合同号』还是『工单号』？」——客户档案表里没有这两列 |
| 答非所问 | 4 | 用户说「做个对比」，模型反问「想用哪种图表」 |

**编造列名与执行类「把派生列名当源列名」同根**：模型学到的是「这类问题该出现某些词」，而不是「该读当前列名清单」。强模型同批问题 100%，因为它每次都真读提示里的列名。

### 6.5 基座是「零」不是「低」

305 条执行类样本 **305 次工具调用为零**。它的 10 条通过全部来自澄清类，经人工核对为真实的计数口径反问（如「员工数是算排班记录还是算人头」）。

结论：1.5B 基座没有工具调用协议的概念，微调解决的首要问题是「会不会调用工具」。

## 7. 关键发现：训练/推理的观察文本不一致（已修复）

复查「微调输入是否用到中间结果表」时发现的三个缺陷。三者都会让模型**在训练时看不到真实工具反馈**。

### 7.1 `create_chart`：训练返回数据预览，推理返回图表地址

| | 文本 |
| --- | --- |
| 训练（修复前） | `操作成功。当前结果为 10 行 × 3 列。字段：[...] 样例：...` |
| 推理 | `图表生成成功：/api/chart/chart_xxx.png\n图表设置：{...}` |

更严重的是：它的观察文本与前一步**100% 完全相同**（实测 1168/1168）。于是画图这一步在上下文里「没有痕迹」，token 损失对漏掉它的惩罚极轻。

**这直接解释了 6.2 节的现象**（`create_chart` 结尾的样本只有 50% 通过），也解释了 6.3 的幻觉—— 模型从未见过「图表生成成功」这句话，所以不会说它，但会把「已经画好了」当成自然结尾。

### 7.2 `describe_data`：训练返回旧措辞，推理返回只读措辞

只读工具改造只改了工具实现，未回填训练数据，512 条样本仍是旧文本。

### 7.3 `describe_data` 在执行器里被当成换表操作

`dataset_builder.executor._apply_step` 把它的产出当新工作副本，而真实工具是只读的（不改 `current_df`）。训练集恰好没有 `describe_data` 处于中间步骤的样本（0/3934），所以一直没暴露。

### 7.4 修复内容

把观察文本生成集中到 `excel_ops.observation_for_step()` 一处，训练与推理共用；`create_chart` 工具本身也改为调用同一个 `chart_observation()`，消除重复实现；`sample_to_messages` 对 `describe_data` 保留原数据副本。

### 7.5 顺带修复：数据构建不可复现

`sample_id` 用了内置 `hash()`（按进程随机化）、图表地址用了 `uuid4()`，导致同一份输入每次生成的数据都不同。改为 `hashlib.sha1` 派生后，两次独立构建的三个文件 sha256 完全一致。

### 7.6 影响范围

| 项 | 结果 |
| --- | --- |
| 样本总数 | 3934（不变） |
| `create_chart` 观察被修正 | 1125 条 |
| `describe_data` 观察被修正 | 486 条 |
| 最长序列 | 5087 → 5217 token |
| `max_length` 默认值 | 4096 → **5376**（避免 4 条截断） |

**训练数据已重新生成。测试 465 项通过，新增 10 项一致性测试。**

## 9. 结论

### 9.1 判断

1. **微调路线成立**。基座 2.5% → v2 74.7%，工具调用从无到有，这一步没有替代方案。

2. **v2 的能力结构是不均衡的**：
   - 单步/短链执行：优于强模型（100% vs 61.9%/42.9%）
   - 多步链执行：与强模型无显著差异，但成因为「v2 漏步骤、强模型多步骤」，性质不同
   - 澄清：明显弱于强模型（B 组 54.8% vs 100%）
   - 表结构迁移：弱，会编造列名
   - 失败处理：弱，会声称做成

3. **当前的 74.7% 里有可修复的水分**。64 条「漏步骤」中，`create_chart` 占 38 次——而这正是第 7 节已定位的观察文本缺陷。修复后重训是当前性价比最高的动作。

### 9.2 下一步优先级

| 优先级 | 动作 | 依据 | 预估成本 |
| --- | --- | --- | --- |
| **P0** | 用新数据训练 v3，验证观察文本修复的效果 | 64 条漏步骤中 38 条是 `create_chart` | 5 小时 |
| **P0** | 注入失败-修正轨迹（造错列名 → 真实报错 → 从「可用字段」恢复） | 编造列名 + 幻觉汇报 | 1 天构造 + 5 小时训练 |
| P1 | 列名泛化训练（随机重命名训练表列） | B 组 4 条编造列名 | 与上一项合并 |
| P1 | 澄清专项（必须点名具体选项） | B 组 6 条泛泛反问 | 数据构造 + 训练 |
| P1 | 执行类测试集扩到每组 700+ 条 | 检测 6.8 点差异需 674 条 | 构建 1 小时 + 评测 1 小时 |
| P2 | 训练 2 epoch | loss 仍在下降 | 10 小时 |

### 9.3 方法论教训

本次实验过程中被修正的评测缺陷（均会显著影响结论）：

| 缺陷 | 后果 |
| --- | --- |
| 评测问法与系统提示冲突 | 按提示澄清计数口径的强模型被判 40%（正确行为被判错） |
| `describe_data` 覆盖中间结果 | 强模型「先看数据」后全线失败，80% → 20% |
| 只读工具多调用一次判失败 | 谨慎的模型被扣分 |
| 结果表按列名对齐 | 模型自由命名的列被判不同，虚低分数 |
| 澄清判据未排除「索要已知信息」 | 基座虚报 7 条通过 |
| 测试集仅 117 条 | 「v2 超强模型 23 点」的结论在 396 条上不复现（实为落后 5.6 点） |
| 训练/推理观察文本不一致 | `create_chart` 结尾样本只有 50% 通过 |

**核心教训：低分先怀疑标签与工具，再怀疑模型。** 本次 6 个评测缺陷里有 4 个是「评测或工具错了，不是模型错了」。
