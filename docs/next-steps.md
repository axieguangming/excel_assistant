## 1. 评测口径修正（优先级最高）

当前评测存在三个方法论问题，若不先修正，后续所有改进都无法准确归因。

> 完整协议、指标定义与复现命令已整理为独立文档：[eval-protocol.md](./eval-protocol.md)。
> 本节保留计划视角的待办与结论。

### 1.1 补测缺失的对照组（已完成）

| 模型 | 新 test 499 | 留出链集 32 条 | 留出集 A / B（396 条） |
| --- | --- | --- | --- |
| 基座 1.5B（未微调） | **0%（0/481）** | 等价类 0/23 | **1.6% / 4.0%** |
| v2 适配器 | 78.8% | 71.9% | **79.8% / 66.4%** |
| 强模型 `deepseek-flash` | — | — | **85.4% / 81.2%** |

实现：`finetune/eval_sft.py` 新增 `--base-url` / `--remote-model` / `--api-key`，复用 `langchain.init_chat_model` 对接 OpenAI 兼容接口。

**强模型仍是最强的对照组，但在「按本项目协议执行」这件事上并不占优。** 它在 396 条上总分领先 v2 9.1 个点，但执行类差距不显著（见上表短板行），且在单步任务上明显弱于 v2：

| 执行类按期望步数 | 强模型 A / B | v2 A / B |
| --- | --- | --- |
| 1 步 | 61.9% / 42.9% | **100% / 100%** |
| 2 步 | **88.4% / 79.5%** | 72.3% / 60.2% |
| 3 步 | 75.9% / 75.0% | **81.5% / 89.3%** |

原因是强模型倾向于「多做一步」——调完 `describe_data` 又用 `aggregate_data` 重算，结果表被换掉。它解决业务问题更强，但严格按 9 个工具、按指定顺序执行时不如微调模型。

若要真正的上限参照，应换更强的模型（`deepseek-chat` 或 GPT 级），并接受它同样会偏离本项目协议。

**v1 适配器不再用于跨数据集对比。** v1 在旧数据分布上训练，拿它测新数据集只说明「没学过该分布」，无法反映能力差异。v1 与 v2 的公平对比只在留出链集上进行（30.4% vs 73.9%）。

### 1.2 增加 train / val 的准确率评测

目前只测 test，导致无法区分「欠拟合」与「泛化不足」：

- val 只记录了 `eval_loss`（0.1006），从未跑过完整 Agent 评测。
- train 从未评测。

判断逻辑：

| train 准确率 | 结论 | 对应措施 |
| --- | --- | --- |
| ≈ test（78%） | 欠拟合，连见过的都复现不了 | 加训练量、调超参，加数据无用 |
| ≥95% | 记住了但不会迁移 | 加数据多样性、正则化 |
| 85% 左右 | 混合 | 两者都要 |

建议：train 分层抽样 400 条、val 全量 498 条（train 全量 3934 条需约 7.6 小时，不现实）。

同时应注意 **teacher-forcing 与自由运行的落差**：`eval_loss` 0.1006 对应很高的逐 token 准确率，但自由运行只有 78.8%，这是曝光偏差。后续应在文档与汇报中区分这两个指标，避免把低 `eval_loss` 误读为「模型很好」。

### 1.3 修正「不可完成请求」的判定（已修正，发现新问题）

旧判定只看「是否调用执行类工具」，对从不调用任何工具的模型天然有利：基座在 9 条上得 100%，实际是它根本没有工具调用能力。

修正后的判定要求同时满足：

1. 不调用执行类工具；
2. 文字答复中含明确的「无法完成 / 需要澄清」表述；
3. **答复里点出了提问中尚未出现的具体选项**（如「指『区域』还是『产品线』」）。

第 3 条是关键：未微调基座会大量输出「请提供您希望使用的图表类型以及数据字段」——形式上也是反问，但它要的是表格里已有的信息，并不指向任何歧义。

**修正后重新测量（18 条澄清样本）**：

| 模型 | 旧判定 | 新判定 |
| --- | --- | --- |
| v2 适配器 | 18/18 = 100% | **10/18 = 55.6%** |
| 基座 | 18/18 = 100% | 7/18 = 38.9%（含关键词巧合，实际接近 0） |

逐条核对 v2 的 8 条失败，**均为真实缺陷**：

| 类型 | 例子 |
| --- | --- |
| 泛泛反问 | 问「按分类」，答「想按什么分类看？请提供具体的分类标准」——未点名可选字段 |
| 答非所问 | 问「最近」的时间范围，答「销售是指销售额还是实收金额」 |
| 幻觉列名 | 问卷表里答「比如『部门』或『地区』」，实际字段是年龄段/城市 |
| 误判列内容 | 说满意度是「满意/一般/不满意」三种评价，实际是 1–5 分 |

**结论**：此前 18/18 的「澄清能力 100%」是旧口径的假象。真实水平约 55%，且存在问题集中在「不点名具体选项」与「幻觉列名」两类。

**残留局限**：该判定仍为启发式（关键词 + 选项词重合），基座的 38.9% 中含关键词巧合，不可直接横向比较。精确结论需人工抽查。

### 1.4 评测集命名

`evalsets/colloquial_2026-10.json` 的名字不准确：v2 的训练数据本身就是口语化的，语言风格不构成新挑战。该集合的真正价值是**链留出**（22/23 条链未在训练集出现）。

建议改名为 `heldout_chains_2026-10.json`，并在文件内注明：表结构仍与训练集相同，属于「留出任务但共享表」的中等强度测试。

## 3. 训练数据补强

### 3.0 P0：注入失败-修正轨迹（新发现，优先级最高）

留出集 B 组的 14 条失败里，**10 条（71%）是「字段找不到」**。原因不在模型容量，在训练数据的构成：

```
训练轨迹     3934 条
工具观察     9017 条
其中报错次数 0 次        ← 0.0%
报错后继续调用的轨迹 0 条
```

所有合成链都是「一次做对」的成功轨迹。模型从未见过工具返回错误后的情况，因此参数一写错就直接放弃：

> 对不起，我漏了运费合计和平均毛重这两项。它们在「运单明细」这张表里没找到，可能是别处的字段。请检查这些字段是否存在。

而工具观察里已经给了恢复所需的全部信息：

> 工具执行失败：找不到字段：['运费合计', '平均毛重', '运单号']。可用字段：['运单编号', '签收日期', '始发站点', '目的站点', '毛重', '运费', '签收结果', '单位运费']

构造方式：

1. 取已生成的正确链，把某个参数里的列名替换成**近似但不存在的名字**（`运费` → `运费合计`、`运单编号` → `运单号`）。
2. 真实执行，抓到工具返回的报错文本。
3. 由强模型或规则从报错里的「可用字段」清单中选出正确列名。
4. 真实执行修正后的链，确认结果正确。
5. 把「错误调用 → 报错观察 → 修正调用 → 结果」四个消息全部写进轨迹。

规模建议 300–500 条。附带收益：模型能学到「不要在答复里声称做了没做的事」——v2 现在存在「柱状图也画好了」但实际没调用 `create_chart` 的幻觉。

### 3.0b P0：列名泛化训练（新发现）

v2 在 B 组把派生列名当源列名的错误共 10 条，例如 `{"column": "运费合计", "function": "sum"}`——`运费合计` 是 `name` 字段该有的名字，不是源列。

成因是训练数据里 `column` 与 `name` 的字面形式高度相关（`销售额` + `销售额合计`），模型学到的是「`X` 求和就叫 `X` 合计」这个字面模式，遇到新域就套错位置。

可尝试的措施：

1. **随机重命名训练表列**：在转 SFT 之前把列名换成同义词或随机代号（`销售额` → `营收额`、→ `col_a`），让模型只能依赖「表里实际有什么列」而不是字面联想。
2. **负样本对**：同一问题，一条参数用正确列名、一条用派生列名（会报错），做成偏好对。
3. **参数约束校验**：在数据生成阶段强制检查所有 `column` / `group_by` / `subset` 字段必须出现在表头里，把这类样本提前杀掉。这一条只能防住「数据里本来就有错」，防不住「模型自己套错」，但成本最低。

### 3.1 P0：排序步骤被系统性忽略

最严重的问题：多步链里 31 条因缺少 `sort_rows` 失败。

成因分析：排序不改变行数与列名，SFT 的 token 似然对「少写一步」的惩罚远小于「写错字段名」。**越是没有副作用的必要步骤，越容易被省略。**

可尝试的措施，按成本递增：

1. **专项样本对**：构造「同一链，一条含排序、一条不含」的成对样本，让模型区分「按 X 排序」与「不排序」的表述差异。
2. **步骤加权**：对 `sort_rows` / `create_chart` 这类易漏步骤对应的 assistant token 提高损失权重。
3. **DPO**：构造 chosen（完整链）/ rejected（缺排序步骤）偏好对，直接惩罚「看似合理但实质错误」的轨迹。这是治本方案，但需要额外的偏好数据与训练流程。
4. **约束解码**（推理侧兜底）：在 `local_llm.py` 或 prompt 中强制检查「问题含排序意图则输出必须包含 sort」，不依赖模型自觉。

### 3.2 P0：补充 4–5 步长链

现状训练集最大 3 步，而 `MAX_AGENT_TURNS=10`。真实用户会提出「筛选 → 加计算列 → 汇总 → 排序 → 画图」这类 5 步需求。

- 生成方式：要求 `LLMChainProposer` 显式产出 `max_steps=4..5` 的链。
- 数量：约 150 条链。
- 风险：命中的工具组合呈指数增长，需检查执行成功率（长链更容易因中间字段不存在而失败）。

### 3.3 P1：补齐覆盖缺口

| 缺口 | 现状 | 补充方式 |
| --- | --- | --- |
| 单步工具 | 只 5/9（缺 filter / aggregate / add_computed_column / create_chart） | 定向生成单步链各 30 条 |
| 筛选操作符 | 6/10（缺 `ne`、`lte`、`contains`、`not_contains`） | 在链生成提示词中显式点名 |
| 日期筛选 | 0 条 | 提示词要求对日期列做 `gt`/`lt`/`gte`/`lte` |
| 错误恢复 | 0 条 | 构造「工具报错 → 读错误 → 修正参数」三消息轨迹 |
| `bfill` / 常数运算 | 14 / 30 次 | 参数均衡抽样 |

### 3.4 P2：不可完成请求专项

现有 9 条中仍有 3 条硬套工具，共同点是**工具名与请求字面相似**（标红→筛选、移动平均→绘图、公式列→计算列）。

补充约 80 条「形似而不可为」的样本，例如：

- 「把重复的行标黄」→ 无格式工具
- 「按周汇总」→ 无日期分组能力（`group_by` 只接受列名）
- 「把两张表拼起来」→ 无 join
- 「自动算出下个月该备多少货」→ 无预测

### 3.5 训练目标与语义脱节（长期）

根本问题：SFT 只优化 token 似然，与「结果表是否正确」不等价。可选方向：

- **结果级验证奖励**：训练后对输出执行一次，把「结果是否正确」作为筛选/重排序信号（类似 rejection sampling）。
- **DPO / KTO**：用「可执行且结果正确」的轨迹作为正例。
- 这在算力有限时更现实的做法是**推理侧校验**：跑完链后用评测逻辑自检，不合格则重试一次。

| 脚本 | 输入 | 用途 |
| --- | --- | --- |
| `finetune/evaluate_local.py` | 数据集批次 | 通用本地模型评测 |
| `finetune/eval_sft.py` | SFT 轨迹目录 | 训后同分布评测；留出集评测；强模型/基座对照 |
| `finetune/evaluate_colloquial.py` | 人工评测集 | 留出链评测 |
| `dataset_builder/cli.py eval` | 数据集批次 | OpenAI 兼容服务评测 |

建议：统一为「加载模型」与「判定逻辑」两部分，判定逻辑抽到 `dataset_builder/eval.py`，避免同一指标在不同脚本里口径不一致（`unanswerable` 的缺陷就是这样产生的）。

`eval_sft.py` 已支持 `--base-url`（强模型）、`--base-only`（基座）、`--tables-dir`（留出集），三模型对照可以完全走同一入口，口径天然一致。

### 4.3 真值一致性维护

`count` 语义变更时，曾出现 24 条真值 CSV 过期。`pipeline/refresh_count_truth.py` 是临时补救脚本。

长期应把「工具语义变更 → 自动检测受影响样本 → 重算真值」纳入常规流程，或在 `pipeline/` 下加一个统一的 `verify_truth.py`。

### 4.4 训练日志与可复现性

当前训练参数、数据版本、评测结果分散在 `build/*.log` 与各 `eval-*.json`。建议在训练结束时自动写一份 `run.json`，记录：

- 数据集路径与 sha256
- 训练参数（epochs / lr / max_length / batch）
- 最终 loss
- 关联的评测报告路径

便于回溯「某个分数对应哪次训练」。

## 5. 执行顺序建议

| 阶段 | 内容 | 状态 |
| --- | --- | --- |
| 一 | 补测强模型 + 修正 `unanswerable` 判定 | **已完成** |
| 二 | 建留出集 A/B 并扩到 396 条，重测三个模型 | **已完成** |
| 二·五 | 修复训练/推理观察文本不一致（`create_chart`、`describe_data`） | **已完成**（代码 + 数据就绪，未训练） |
| 三 | **用新数据重训 v3，验证观察文本修复的效果** | **下一步，最高优先级** |
| 四 | 注入失败-修正轨迹 + 列名泛化训练，重训 | 待做 |
| 五 | 补 P0 数据（5 步以上长链、覆盖缺口） | 视结果而定 |
| 六 | 执行类测试集扩到每组 700+ 条 | 与阶段三并行可做 |
| 七 | 建留出集 C（新结构 + 4–5 步长链） | 依赖阶段五 |

**阶段二·五的前提**：`create_chart` 的观察文本在训练侧是数据预览、推理侧是图表地址，且与前一步 **100% 相同**，导致画图这一步在上下文里没有痕迹。64 条「缺少步骤」里 38 条就是它。修复后训练数据已重新生成，但**适配器仍是旧数据训的**。

阶段三的关键判据：**以 `create_chart` 结尾的 86 条样本，通过率能否从 50.0% 提上来。** 若提到 75% 以上，A 组执行类应能从 78.1% 涨到 85% 左右；若纹丝不动，说明模型漏步骤另有原因（如损失权重），需要转做步骤加权或 DPO。

关键原则：**每一步都要有可对比的基线**。当前基线是 `build/exp-{a,b}-{strong,base,v2}.json`（396 条）。
注意：**重训只需重跑 v2 一组**——强模型与基座的输入路径（系统提示词、工具 schema、工具输出）本次均未改变，已逐项核验，其 83.8% / 2.5% 可继续复用。

## 6. 明确不做的事

| 事项 | 原因 |
| --- | --- |
| 用 v1 适配器测新数据集 | 训练分布不同，结果无解释力 |
| 扩大到 10 步以上的链 | 1.5B 模型的上下文与决策深度难支撑，性价比低 |
| 让模型生成并执行 Python 代码 | 违反项目设计原则（见 [dataset-plan.md](./dataset-plan.md) 第 1 节） |
| 用规则模板问法评估模型能力 | 与训练同源，测的是记忆 |
| 把 `deepseek-flash` 当能力上限汇报 | 它在留出集 A 低于微调模型，且失败形态是本项目协议不适配 |
| 在留出集问法里使用「X数」 | 与 `AGENT_SYSTEM` 的澄清要求冲突，会把正确行为判成错误 |
