# Excel Agent 微调数据集构造方案

本文档定义 Excel Agent 微调与评测数据集的构造流程、样例格式、质量校验、数据划分与评测口径。适用于训练可在用户本地运行的小模型，也适用于后续模型蒸馏和远程模型基线比较。

## 1. 目标与边界

训练目标是让本地小模型稳定驱动现有 Excel 工具：从用户需求识别意图、生成合法的工具调用与参数、读取工具返回并决定下一步，直到任务完成或需要澄清。**表格计算由工具代码执行，模型不生成、也不执行任意代码。**

数据范围以 Excel 用户的常见需求为准，并与当前工具能力对齐：

| 需求类别 | 对应工具 | 状态 |
| --- | --- | --- |
| 查看与统计概况 | `describe_data` | 已支持 |
| 筛选 | `filter_rows` | 已支持 |
| 排序、Top N | `sort_rows`、`top_n_rows` | 已支持 |
| 分组汇总 | `aggregate_data` | 已支持 |
| 去重 | `deduplicate_rows` | 已支持 |
| 缺失值填充 | `fill_missing_values` | 已支持 |
| 新增计算列 | `add_computed_column` | 已支持 |
| 图表 | `create_chart` | 已支持 |
| 查找与合并、透视、格式与公式编辑 | — | 暂不支持 |

暂不支持的需求仍应出现在数据集中，但标签应是澄清或明确说明无法完成，不能虚构并不存在的工具能力。

### 参数约束

工具参数必须符合 [schemas.py](../schemas.py) 的定义，构造操作链时需遵守：

- `filter_rows`：每个条件包含 `column`、`operator`、`value`；`operator` 仅限 `eq`、`ne`、`gt`、`gte`、`lt`、`lte`、`contains`、`not_contains`、`is_empty`、`not_empty`；至少一个条件，多个条件同时满足。
- `aggregate_data`：`metrics` 至少一项，`function` 仅限 `sum`、`mean`、`min`、`max`、`count`、`nunique`；`group_by` 可为空表示整体汇总。
- `top_n_rows`：`limit` 取值范围 1–10000，且必须提供排序字段。
- `sort_rows`：`sort_by` 至少一项，每项包含 `column` 与 `ascending`。
- `deduplicate_rows`：`subset` 为空表示按整行判重。
- `fill_missing_values`：`fill_strategy` 仅限 `ffill`、`bfill`、`value`；`value` 策略需要非空标量 `fill_value`。
- `add_computed_column`：`operator` 仅限 `add`、`subtract`、`multiply`、`divide`；`right_column` 与 `right_value` 必须且只能提供一个；`name` 不能与现有字段重名；`round_digits` 取值范围 0–10；除数为 0 时返回错误。
- `create_chart`：`chart_type` 仅限 `bar`、`line`、`pie`、`scatter`；`chart_y` 为数值字段；散点图必须提供 `chart_x`。

Agent 当前最大模型决策轮数为 `MAX_AGENT_TURNS = 10`（见 [agent.py](../agent.py)），多步操作链通常为 1–10 次工具调用。

## 2. 数据来源

**当前实现只使用仿真生成表格**（见 2.2），因此数据集不涉及第三方许可或个人信息；公开表格与真实需求来源保留为后续扩展，尚未在本仓库实现。

### 2.1 有许可的公开表格（后续扩展，当前未实现）

- 候选来源：开放数据平台、政府开放数据、明确标注许可的公开数据集、学术数据集。
- 优先选择具有实际业务语义的数据，例如销售、库存、订单、预算、排班、调查统计。
- 每个数据源入库前登记：来源、许可类型、下载日期、是否允许用于训练、是否允许再分发、是否包含个人信息。
- **可下载不等于可用于训练或再分发**，许可不明确的数据源不得进入训练集。
- 含个人信息或敏感字段的表格应排除，或先完成去标识化再评估。

### 2.2 仿真生成表格（当前实现）

按常见业务场景生成表格与任务，输出为 `.xlsx`。可控覆盖：

- 日期、数值、分类文本、混合类型列；
- 空值、重复行、异常值、全空列；
- 相似或容易混淆的列名；
- 少量行、无匹配结果、超宽表等边界；
- 多种字段命名与表结构，避免模型记住单一模板。

### 2.3 经授权的真实需求（后续扩展，当前未实现）

- 后续可在产品中明确告知并取得用户同意后，收集**去标识化的需求文本与纠正反馈**。
- 默认不留存用户上传的工作簿；确需保留时，须单独约定用途、保留期限与删除方式。
- 未经授权的用户表格不得进入数据集。

## 3. 核心流水线

大模型负责语义质量，程序负责有效性与真值。

```
① 采集或生成表格
   ↓
② 大模型按能力规范生成候选操作链
   ↓
③ 程序校验（工具名、列存在、类型、前置条件、步骤可达）
   ↓        ← 不通过则回退修正或丢弃
④ 工具逐步执行，记录每步输入、输出与最终结果
   ↓
⑤ 强模型根据已执行的操作链生成自然语言问题
   ↓
⑥ 一致性校验：问题反向解析为操作链，与原链比对
   ↓        ← 不一致则丢弃或人工审核
⑦ 程序将操作链映射为工具调用轨迹
   ↓
⑧ 保存训练样本、验证状态与来源记录
```

### 3.1 表格准备

- 表格以 **`.xlsx`（Excel）为默认格式**写盘，与真实用户上传的文件一致；CSV 仅作为可选格式保留。
- 建样本前会把表格**从 Excel 文件重新读取**，用读回后的数据执行操作链。这样真值反映的是用户上传该文件后实际拿到的数据，而不是内存中的生成结果——Excel 往返会改变部分类型（例如带空值的整数列变成浮点）。
- 保存工作簿 ID、工作表名、列类型、行列数、缺失率等元信息；索引同时记录生成时的逻辑类型（`kind`）与写盘后读回的类型（`stored_kind`）。
- 传给模型的上下文只包含表头、字段类型和少量脱敏样例，不必传整张真实表。
- 当前每个工作簿只包含一个工作表，因为应用上传时只读取第一个工作表；多工作表工作簿的处理尚未纳入数据集范围。

### 3.2 操作链生成

- 向模型提供工具清单、参数 schema、字段约束和执行前置条件。
- 要求模型输出**结构化 JSON**，而不是自然语言描述。
- 设定覆盖配额，避免模型只生成简单、常见的任务。当前实现在提示词中要求 9 类能力各至少出现一次，并在流水线内按类别签名优先排序候选。
- 多步链需保证每一步的输入是上一步的输出，例如汇总后原表中被聚合掉的字段不能继续引用。

#### 规则生成（`--proposer template`）

不调用任何模型，按"列 × 操作符 × 参数 × 步数"组合枚举候选链。实测每张表可产出
244–472 条不同链，足以支撑上千条样本。要点：

- 阈值取自各列实际分位数（0.25/0.5/0.75），不是固定 0，因此不同表参数不同；
- TopN 的 `limit` 在 5/10/20 之间变化，图表类型与坐标列组合展开；
- 计算列覆盖数值列两两组合与常数运算；
- 多步链包含"汇总→排序""汇总→绘图""汇总→TopN""筛选→TopN""计算列→TopN""计算列→汇总"
  等真实组合。

生成约 1000 条时的推荐参数是 `--table-count 45 --per-table 24 --max-attempts 30`：
`--max-attempts` 默认 12 会成为瓶颈（每表只能出 12 条链），批量生成必须调大。

#### 问法多样性

同一操作链可以配多条同义问法（`--variants N`）。固定句式重复上千次会让模型记住模板，
所以 `TemplateQuestionWriter` 内置 7 套句式模板，按表名与序号稳定选择。

注意 `--variants` 会挤占每张表的样本配额：`--per-table 24 --variants 3` 只会用到 8 条链，
链的多样性反而下降。批量生成时建议 `--variants 1`，靠增加表数量提升多样性。

### 3.3 程序校验

在写入数据集前校验：

- 工具名在白名单内；
- 引用的列在当步输入表中存在；
- 操作符与字段类型匹配，例如不应对文本列做 `sum`；
- 参数满足 schema 约束；
- 多步链可顺序执行，中间表仍包含后续步骤所需字段；
- 图表参数合法，例如散点图有 `chart_x`。

校验不通过时，允许模型在限定次数内修正；仍失败则丢弃，并记录失败原因用于改进提示词。当前实现按 `--max-attempts` 限制每张表的候选链数量，并对问题反向解析做 2 次带错误反馈的重试（`BuildConfig.parse_attempts`）。

### 3.4 执行与真值

- 使用现有工具真实执行操作链，保存每一步的结果。
- 操作链、参数、中间状态与最终结果都来自实际执行，而不是模型声称。
- 执行异常、结果为空但用户需求本应有结果的情况，需要单独标记，不能直接当作正确样本。

### 3.5 自然语言问题生成

- 问题应完整、忠实地表达操作链，不增加链中没有的条件或步骤。
- 不泄漏工具名、参数格式或内部实现细节。
- 可以生成少量同义改写，但必须绑定同一条操作链。
- 对歧义需求，标签应是澄清问题，而不是猜测执行。

### 3.6 一致性校验

- 使用独立的验证步骤将问题解析回规范化操作链，与原链比较。
- 生成与验证不应复用同一次模型输出。
- 当前实现的判据是**执行结果一致**，而不是链文本一致：解析出的链会重新执行，再与真值结果比对形状和数据。这样可以容忍 `name` 重命名等纯表现差异，同时仍能拦住语义不同的解析（例如汇总后错误引用原始列名会导致执行失败）。
- 解析失败时最多重试 `parse_attempts` 次，并把上一次的 schema 错误反馈给模型。
- 不一致的样本丢弃或进入人工审核。
- 建议同时记录一致性判定的依据，便于复核。

### 3.7 轨迹转换

- 操作链已是结构化数据，工具名与参数**由程序映射**为调用轨迹。
- 不再让模型重新生成一份轨迹，避免与已执行结果不一致。
- 轨迹应保留“调用 → 观察 → 下一步”的完整循环。

### 3.8 当前实现

代码位于 [dataset_builder/](../dataset_builder)：

| 模块 | 职责 |
| --- | --- |
| `tables.py` | 生成 5 类仿真业务表（订单、库存、排班、预算、问卷），可控注入空值、重复行、全空列，并导出/加载表格索引 |
| `chain.py` | 操作链规范化：工具白名单、参数 schema、步数上限、链等价比较 |
| `executor.py` | 用 `excel_ops` 的真实算法逐步执行，产出中间结果与最终真值 |
| `llm.py` | 大模型适配：生成候选操作链、生成问题、反向解析问题 |
| `templates.py` | 离线确定性生成器与中文表述，用于自测和冒烟 |
| `pipeline.py` | 串联流水线、落盘样本与结果、回放校验 |
| `split.py` | 按 `workbook_id` 分组划分并检测泄漏 |
| `cli.py` | 命令行入口 |

```powershell
# 离线模板生成（不调用模型，适合验证流程）
python -m dataset_builder.cli build --out datasets --table-count 6 --per-table 6

# 规则方法批量生成约 1000 条（纯本地，无 API 费用）
python -m dataset_builder.cli build --out datasets --table-count 45 --per-table 24 `
  --max-attempts 30 --max-steps 4 --seed 20261026

# 用已配置的远程模型生成操作链与问题（会产生 API 费用）
python -m dataset_builder.cli build --out datasets --table-count 30 --per-table 10 --proposer llm

# 复用已有表格，只用模型生成样本
python -m dataset_builder.cli build --out datasets --tables-dir datasets/2026-10-23/tables --per-table 8 --proposer llm

# 需要 CSV 而不是 Excel 时显式指定
python -m dataset_builder.cli build --out datasets --table-format csv

# 让构建落到指定日期（便于复现历史批次）
python -m dataset_builder.cli build --out datasets --date 2026-10-23

# 回放校验：自动使用 datasets 下最新的日期目录
python -m dataset_builder.cli replay --data datasets
```

输出目录（每次构建独立归档，同一天多次构建自动加序号）：

```
datasets/
  2026-10-23/                  # 构建日期目录；同日再构建为 2026-10-23-2
    tables/index.json          # 表格索引、工作表名、列类型、来源许可
    tables/<table_id>.xlsx     # 仿真表格（Excel）
    samples.jsonl              # 通过的样本
    rejects.jsonl              # 被拒样本及原因
    results/<sample_id>.csv    # 最终结果真值
    splits/{train,val,test}.jsonl
    report.json                # 覆盖度、拒绝原因、分区计数
    eval-<split>-<model>.json  # 该数据集上的评测报告
```

读命令（`replay` / `eval` / `resplit`）把 `--data datasets` 自动解析到**最新的日期目录**，
也可以用 `--data datasets/2026-10-23` 指定历史批次。用 `--date 2026-10-23` 可以让构建
落到指定日期；`--no-date-dir` 则退回旧行为（直接写进 `--out`，会覆盖同名文件）。

这样安排的原因：一次构建会生成表格、样本、真值和报告一整组文件，写进同一目录会互相覆盖，
而覆盖后既无法复现旧实验，也无法对比两次生成的数据差异。

被拒原因：`invalid_chain`（工具或参数不合法）、`execution_failed`（列不存在、类型不适用等）、`question_failed`（问题生成失败）、`question_mismatch`（反向解析失败或执行结果与真值不一致）。

### 3.9 示例运行结果

用远程模型在 12 张仿真 Excel 表上生成的结果：

| 指标 | 数值 |
| --- | --- |
| 表格 | 12 个 `.xlsx` 文件 |
| 样本 | 96 条（全部 `auto_passed` / `llm_verified`） |
| 拒绝 | 3 条（均为 `describe_data` 之后绘图，汇总结果中已无原字段） |
| 工具类别 | 9/9 全覆盖 |
| 难度 | simple 9 / multi_step 86 / complex 1 |
| 分区 | train 80 / val 8 / test 8 |
| 回放校验 | 96 条全部一致 |

生成过程中的三个实测结论：

1. **按链文本比对会把大量有效样本误判为不一致**：模型给汇总列起别名（如 `name="销售额合计"`）时，反向解析不会复现该别名。改为执行结果比对后，单表产出率从 17% 提升到 80% 以上。
2. **解析器容易在汇总后继续引用原始列名**，导致链不可执行。在解析提示词中说明汇总列名规则（`字段_函数` 或 `name`）后，该类失败基本消失。
3. **CSV 与 Excel 的读回结果不同**：Excel 往返会把带空值的整数列变成浮点列。因此真值必须在 Excel 读回的表格上计算，否则样本与用户实际看到的数据不一致。

这批数据只是小规模验证，尚未达到 6.1 的试点规模，也未经人工审核。

### 3.10 规则批量生成结果（约 1000 条）

用 `--table-count 45 --per-table 24 --max-attempts 30 --max-steps 4` 生成：

| 指标 | 数值 |
| --- | --- |
| 表格 | 45 个 `.xlsx` |
| 样本 | 1072 条（全部 `auto_passed` / `structural`） |
| 唯一操作链 | 711 条（平均每条重复 1.5 次） |
| 不同问法 | 1032 / 1072 |
| 拒绝 | 32 条（均为 `execution_failed`） |
| 难度 | simple 626 / multi_step 446（多步 42%） |
| 工具类别 | 9/9 全覆盖，图表 131 条 |
| 分区 | train 880（37 表）/ val 96（4 表）/ test 96（4 表） |
| 回放校验 | 1072 条全部一致 |

第一版实现的两个教训（已修复）：

1. **候选链池太小**：旧生成器每表只有约 16 条链，1040 条样本里唯一操作链仅 77 条，
   单步任务占 85%。原因是候选按固定几列硬编码。改为按列与参数组合枚举后，候选池
   提升到 244–472 条/表，唯一链升到 711 条、多步占比 42%。
2. **`--max-attempts` 默认值是隐藏瓶颈**：它把候选截断到 12 条，导致 `--per-table 24`
   实际只能产出 12 条。批量生成必须显式调大。

数据分区仍按工作簿分组：`test` 的 4 个工作簿覆盖全部 9 类任务，且与 train 无重叠。

### 3.11 图表任务与标签质量修正

用远程模型评测这批数据后发现，**失败几乎全部来自标签而非模型**，据此修正了生成器：

| 修正 | 原因 |
| --- | --- |
| 新增 `aggregate → chart`、`aggregate → sort → chart`、`filter → aggregate → chart` | 原生成器的图表任务 100% 是"直接按原始行画图"。明细表一行一条记录、类别只有几个时，直接绘图会堆叠大量重复项，先汇总才是对的 |
| 单步绘图保留，但加两个守卫 | ① 行数远多于类别数（`行数 > max(类别数*3, 12)`）时跳过，避免退化任务；② 每行都不同的列（订单号/编号）不作为分类轴 |
| 排除全空列 | 全空列在 pandas 里被推断成 `float64`，混进"数值列"后生成"空列 + 数值"这类必然全空的计算任务。修复前 1080 条中有 88 条命中 |
| 不再生成 `sort_rows → top_n_rows` | `top_n_rows` 内部已按同字段排序，前一步排序对结果无影响，属冗余标签 |

修正后的图表任务分布（263 条）：`aggregate→chart` 116、`aggregate→sort→chart` 53、单步 49、
`filter→aggregate→chart` 45。单步仍保留约 19%，但不再是唯一形态。

### 3.12 远程模型基线（deepseek-flash）

在 1080 条规则生成数据集上的评测结果：

| 指标 | 修正前（1072 条） | 修正后（1080 条） |
| --- | --- | --- |
| test 任务成功率 | 94.79% | **100%** |
| test 工具序列一致 | 90.62% | **98.96%** |
| test 首个工具正确 | 91.67% | **100%** |
| test 图表产出率 | 100%（16 条） | 100%（22 条） |
| train 任务成功率 | 93.86% | — |

修正前 test 的 5 条失败全部是标签侧问题（模型多做了一步合理汇总，或标签本身退化）；
按"失败是否为标签侧"重新归类后，估计真实成功率已达约 100%。修正后仅剩 1 条序列差异
（模型多做了一次冗余 `sort_rows`，结果仍一致）。

这条经验值得记住：**低分先怀疑标签，再怀疑模型**。规则生成的数据集尤其容易出现
"技术上可执行、语义上退化"的任务，而这类任务只有用真实模型跑一遍才会暴露。

## 4. 样本格式

每个样本保存为 JSONL 一行，工作簿与结果文件通过 ID 引用。

```json
{
  "sample_id": "wb00123-task07",
  "source": {"type": "synthetic", "license_id": "L-0007"},
  "workbook_id": "wb00123",
  "sheet": "订单明细",
  "user_request": "只看华东地区金额大于1000的订单，按金额从高到低取前20条",
  "task_categories": ["filter", "top_n"],
  "difficulty": "multi_step",
  "expected_actions": [
    {
      "tool": "filter_rows",
      "args": {
        "filters": [
          {"column": "地区", "operator": "eq", "value": "华东"},
          {"column": "金额", "operator": "gt", "value": 1000}
        ]
      }
    },
    {
      "tool": "top_n_rows",
      "args": {
        "sort_by": [{"column": "金额", "ascending": false}],
        "limit": 20
      }
    }
  ],
  "step_results": [
    {"tool": "filter_rows", "ok": true, "rows": 128, "columns": ["..."]},
    {"tool": "top_n_rows", "ok": true, "rows": 20, "columns": ["..."]}
  ],
  "expected_result": {
    "artifact": "results/wb00123-task07.csv",
    "row_count": 20,
    "columns": ["..."],
    "sha256": "..."
  },
  "expected_response": "已筛出华东地区金额大于1000的订单，并按金额降序返回前20条。",
  "verification": {
    "state": "auto_passed",
    "execution": "passed",
    "question_consistency": "llm_verified",
    "checked_at": "2026-10-23T02:45:31+00:00"
  },
  "provenance": {
    "proposer": "LLMChainProposer",
    "writer": "LLMQuestionWriter",
    "prompt_version": "dataset-v1",
    "created_at": "2026-10-23T02:45:31+00:00"
  }
}
```

### 字段说明

| 字段 | 说明 |
| --- | --- |
| `sample_id` | 唯一样例编号 |
| `source` | 来源类型与许可记录编号 |
| `workbook_id` | 对应工作簿，表格文件单独保存 |
| `sheet` | 工作表名 |
| `user_request` | 用户自然语言需求 |
| `task_categories` | 任务类别，用于覆盖度统计 |
| `difficulty` | 简单、组合、歧义、边界等 |
| `expected_actions` | 期望工具调用序列与参数 |
| `step_results` | 每步执行结果的摘要，便于定位断点 |
| `expected_result` | 最终结果产物与关键断言 |
| `expected_response` | 最终回复要点或澄清问题 |
| `verification` | 校验状态与时间 |
| `provenance` | 生成模型、提示词版本与创建时间 |

`verification.state` 取值：`auto_passed`、`human_approved`、`needs_review`、`rejected`。当前流水线只会产出 `auto_passed`（执行与问题校验都通过）或 `needs_review`（跳过了问题反向解析）。`verification.question_consistency` 取值：`llm_verified`（反向解析比对通过）、`structural`（模板生成器直接由操作链产生问题，未做独立解析）、`unverified`。

## 5. 数据划分与防泄漏

- 划分为训练集、验证集、测试集。
- **按工作簿、数据源、模板或业务场景分组划分**，不按任务行随机拆分。
- 同一表格的改名副本、同一模板的变体、同一操作链的不同问法，必须落在同一分区。
- 测试集冻结，不参与训练、提示词调优或反复筛选。
- 另设人工审核的挑战集，覆盖：
  - 歧义请求；
  - 空结果；
  - 无效列名；
  - 全空列；
  - 多步链中途失败；
  - 超长表和大宽表。

版本化数据集与校验文件，记录每次增删，保证实验可复现。

### 5.1 分层抽样（当前实现）

单纯按工作簿随机分组会产出"测试集只有一个工作簿、且全是图表任务"这种无法解释的分数。
当前实现改为**贪心类别覆盖**：

- 先为 test 挑选能覆盖最多任务类别的工作簿，再为 val 挑剩下的，其余进 train；
- val/test 至少各有 `min_eval_workbooks`（默认 2）个工作簿，工作簿过少时自动降低，但保证三个分区都非空；
- 同一工作簿仍整体落在同一分区，不引入泄漏。

重新划分已有样本不需要重跑模型：

```powershell
python -m dataset_builder.cli resplit --data datasets --seed 20251023
```

`resplit` 会输出每个分区的样本数、工作簿数、图表数和覆盖的类别，便于核对分层效果。
实测把 test 从"1 表 / 8 条 / 4 条图表"改善为"2 表 / 16 条 / 9 类任务全覆盖"。

## 6. 规模与迭代节奏

### 6.1 试点阶段

- 约 30–50 份不同工作簿，当前全部来自仿真生成；
- 约 300–500 条任务，覆盖全部现有工具与多步组合；
- 全部可自动执行与验证，抽样人工审核；
- 目的是验证格式、校验器与审核流程，**不足以证明模型达到产品级效果**。

### 6.2 扩展阶段

- 流程稳定后扩展到数千条高质量样例；
- 扩充依据是评测暴露的失败类型，例如某工具参数错误、某类多步链中断、澄清缺失；
- 不以增加相似问法数量作为主要扩充手段。

### 6.3 持续阶段

- 针对失败类别补数据或补工具能力；
- 统一重跑评测，保持训练、验证、测试口径不变。

## 7. 训练数据形态

- **监督微调**：以对话加工具调用轨迹组织，让模型学习“调用 → 观察 → 继续或结束”。
- **重点样本**：多步组合、参数边界、工具错误后的修正、需要澄清、不可完成需求的说明。
- **蒸馏**：使用强模型在同一批 Excel Agent 任务上的决策轨迹作为教师信号；学生模型学习决策与参数，不学习表格计算。
- **负样本处理**：无效链与错误参数不作为正例；可构造“发现错误并修正”的成对样本，但修正后的链必须经程序执行验证。
- **数据保存**：每行一个任务样例，工作簿与结果产物单独保存并用 ID 引用；结果验证器独立实现，训练与评测共用同一验证逻辑。

## 8. 评测口径

同一套冻结测试集，同时评测远程模型基线与候选本地模型：

- 任务成功率：最终结果与期望一致；
- 工具选择正确率；
- 参数正确率；
- 多步链完整率与断点位置；
- 澄清判断正确率；
- 不可完成需求的说明正确率；
- 平均工具调用轮数与 `MAX_AGENT_TURNS` 触顶率；
- 目标机器上的首 token 延迟、单任务耗时、内存占用、模型体积。

只看回复文本质量会高估实际能力，**“是否真正完成操作”必须是主指标**。

评测已实现为 `dataset_builder.cli eval`，它驱动应用真实的 Agent 图，比对结果表后输出上述指标。
结果比对同时报告"有序一致"与"仅行序不同"两种口径，避免把排序差异与内容错误混为一谈。
延迟、内存等部署侧指标需要单独在目标机器上测量，目前不在该脚本范围内。

### 8.1 图表任务专用判定

`create_chart` 不会写 `result_df`，若沿用"必须有结果表"的判定，图表任务的失败原因
会被误报成 `no_result`，掩盖真实问题（没画图 / 漏了前置步骤）。因此图表类任务单独判定：

| 失败原因 | 含义 |
| --- | --- |
| `no_tool_call` | 完全没有调用任何工具 |
| `no_chart` | 调用了工具，但没有产出图表文件 |
| `chart_ok_but_data_mismatch` | 图画出来了，但数据与期望不符（通常漏了汇总/筛选） |

指标中额外报告 `chart_samples` 与 `chart_produced_rate`，用于区分"不会画图"和"画错了"。
